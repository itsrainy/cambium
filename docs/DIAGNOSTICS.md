# `cambi` diagnostics

Every warning and error carries a stable code, assigned once and never reused; retired codes stay, marked retired. Human form follows `rustc`: `warning[CAMBI-W004]: <message>`, `  --> path:line` if located, `  = help:` if fixable. Under `--format json` it's `{"code", "level", "message", "location", "help"}` in the `diagnostics` array; under `jsonl`, one `{"event": "diagnostic", ...}` line each. Warnings never change the exit code; a log line (`--log info`) is never a diagnostic.

## Warnings

| code | when it fires | what to do |
|---|---|---|
| `CAMBI-W001` | a deprecated spelling still worked: `baseline` for `index`, old `index <query>` for `inspect <query>`, `index inspect` for `index show`/`inspect target`/`inspect package`, bare `config` for `config show`, `--output` for `--format`, `text` for `human` | Switch to the spelling the message names; the help says the old one is removed after one release. One line per invocation on stderr; `--quiet` silences it |
| `CAMBI-W002` | `cambium.toml` sets a key `cambi` no longer honours | Delete it; message names its replacement, if any |
| `CAMBI-W003` | a stored index was skipped: `config_hash` doesn't match this workspace | Expected right after a `cambium.toml` edit or a `cambi` upgrade: a run under the new configuration mints a new lineage (`cambi index build --publish`, or the next post-merge `index update`). Repeats mean the store holds another configuration's indexes; in a pull-request job that edits `cambium.toml` it means the job should test `//...` (docs/CI.md, "Lineage breaks") |
| `CAMBI-W004` | a `.bazelrc` edit could move the graph: a flag on a line the index query reads (`common`, `always`, `query`; under no `--config`, or one in effect) that isn't on the loading-irrelevant allowlist, a `--config` no rc file defines, an unresolvable `import`, a startup flag, an rc file added or removed. The screen only answers when the rc texts at both ends of the range can be read: a `.bazelrc` the run cannot read at either end is in neither chain, so the screen never sees the edit and the invalidator answers it as `CAMBI-W013` instead; run answered `//...` | Allowlist the flag in `[bazelrc].allowlist_extra` if it can't change what `bazel query` loads. A flag under a `--config` the query doesn't run with is already ignored; `[bazelrc].configs` names the ones it does run with. docs/OVER_REPORTING.md has the model and the per-flag evidence |
| `CAMBI-W005` | dirty packages failed to load under `--keep_going` and were tombstoned rather than carried forward: either no `BUILD` file is on disk, so the package reads as deleted, or the `BUILD` file this change edited is the one that fails to load, so rows predating the edit would report its own targets unaffected. In the second case the message names the first five packages | If those packages should load, fix the load error Bazel reported. With no `BUILD` file on disk, the help says where Bazel's stderr is: the `stderr=` field of the `WARN` line logged during the query phase, at the default `--log` level (the warning itself prints after the narration, so other lines sit between them). For an edited `BUILD` file that fails, `bazel query` on its package shows the error. Consumers are reported as affected either way |
| `CAMBI-W006` | `bazel query //...` finished with errors: index is partial. The message names the first five packages Bazel named, and counts the rest | Fix load errors, or name the expected ones in `baseline.publish_partial` (`--allow-partial` for one run) |
| `CAMBI-W007` | a store read came back as absent when it may not be: a `command` fetch failed with stderr output and was read as a miss (the first one in a run; a command that prints nothing when it fails, such as `aws s3 cp --quiet`, gets no warning); a `dir` store's directory does not exist, so it was read as empty (once per run; the run builds cold, or exits 4 under `--no-full-build`); or `status`/`doctor` could not reach the store | Check credentials, the bucket or the path in `[baseline].store`. A missing directory is expected until the first `--publish` creates it; a relative `path` is read from the workspace root. docs/STORE.md, "Misses and outages", says what each backend reads as a miss |
| `CAMBI-W008` | the base index carries no Skyframe loading layer, so which packages the change moved can't be answered; run went global | `cambi index build` against a Bazel that can run `dump --skyframe=deps` |
| `CAMBI-W009` | a changed `.bzl` is one the module system loads (`WORKSPACE` or the module closure) and the index can't name the repositories it defines; run went global | Expected for a workspace-level `.bzl`; else rebuild the index |
| `CAMBI-W010` | retired with the static `.bzl` load closure's witness. The loading layer's `BZL_LOAD` edges are Bazel's own, so there's no stored closure left to be incomplete | Nothing; the code is not reused |
| `CAMBI-W011` | the base index this run computed couldn't be published | The answer is unaffected; check that `[baseline].store` is writable, or the next run computes the base again |
| `CAMBI-W012` | dirty set exceeded `limits.max_dirty_packages`; run re-indexed at head | Still exact, just slower. Raise the limit, or 0 to never cold-rebuild |
| `CAMBI-W013` | a changed path matched an invalidator, so everything is affected. A `.bazelrc` edit is one of these whenever the rc screen has no rc texts to diff (no revisions to read the chain from at either end), because the screen defers to the invalidator rather than guessing: the same edit reads as `CAMBI-W004` when both texts are readable | If it can't move the graph, drop it from `[invalidators]`, or add to `[ignore].globs` |
| `CAMBI-W014` | the external-repository stage couldn't account for a change, escalating to global; includes an rc line the query reads changing `--registry` while `MODULE.bazel.lock` didn't move with it | `[externals].enabled = false` disables the stage if precision isn't wanted. For the registry case, commit the regenerated lockfile with the registry change |
| `CAMBI-W015` | a Starlark build setting a `.bazelrc` edit changed couldn't resolve against the index; run went global | Message says why. Move the setting in-repo, or allowlist it |
| `CAMBI-W016` | `MODULE.bazel` and `WORKSPACE` both present with no `.bazelversion`: which Bazel honours depends on whichever runs, describing different graphs | Pin the version in `.bazelversion`, or delete the file the build does not use; `cambi status` names the inert one once pinned. Pinning is the fix that sticks in a WORKSPACE repository: Bazel 7 writes an untracked `MODULE.bazel` stub into one the first time it runs there, cambi's own queries included |
| `CAMBI-W017` | the Bazel that answered `--version` is older than the oldest major cambium is tested against | Upgrade or pin a tested version; untested is unverified, not refused |
| `CAMBI-W018` | a stored index predates this `cambi`'s on-disk format, so it can't be spliced onto | Mint a fresh lineage (`cambi index build --publish`). On a directory store `cambi index gc` then removes the old one, whatever its age; on S3 or GCS the prefix's lifecycle rule ages it out |
| `CAMBI-W019` | the store holds a lineage with a mismatched `config_hash`, or from an engine with a different rule-hash or content revision | Expected right after a config edit or a `cambi` upgrade; the stale lineage is skipped, never used. On a directory store `cambi index gc` removes it now, whatever its age; `--keep-incompatible` keeps it, for a store another configuration or an older `cambi` still reads. On S3 or GCS the prefix's lifecycle rule ages it out |
| `CAMBI-W020` | `cambi init` found a `.gitignore` not mentioning `cambium.local.toml` | Add the line: it holds machine-local paths and binaries, and committing them makes them everybody's |
| `CAMBI-W021` | `cambi inspect verify` couldn't run `rdeps` for one sampled target, and skipped it (`checked` counts only compared targets); or the `allpaths` query that splits a sample's misses into round trips through an external repository failed, and the misses are listed as plain misses | Run the query by hand (`bazel query 'rdeps(//..., <label>)'`) to see why Bazel refused it; the verdict over the other samples stands |
| `CAMBI-W022` | `bazel mod dump_repo_mapping` stdout wasn't a JSON object, so identity mapping stood in for the real one; a renamed `bazel_dep` can then name the wrong repository | Run `bazel mod dump_repo_mapping ""` in the workspace and check stdout is one JSON object (a wrapper script printing to stdout is the usual cause); rebuild once fixed. If Bazel printed one object and this still fired, report it with that output |
| `CAMBI-W023` | a `toolchain`, `platform`, `toolchain_type`, `constraint_setting` or `constraint_value` rule was added, changed or removed in some package; or a `register_toolchains` / `register_execution_platforms` call moved in `MODULE.bazel`, in a `*.MODULE.bazel` segment the root includes, or in `WORKSPACE`; or this commit moved an external repository that such a call offers rules from; toolchain resolution has no query-graph edge, so everything is affected | Expected; nothing to configure. The message names the rule, the file or the repository. The rule is by class, not by path, so no `[invalidators].globs` entry is needed for the directories that hold declarations. The rule-class half is decided after the query, so `affected --dry-run` can plan a splice and the run still answer `//...` |
| `CAMBI-W024` | a module Bazel autoloads native rules from (`rules_python`, `rules_java`, `rules_shell`, `protobuf`, `rules_android`) moved in `MODULE.bazel`, its lock or `WORKSPACE`, and the Bazel here autoloads: 8 at its default, or 7.4 with `--incompatible_autoload_externally` set in `.bazelrc` (an unknown version counts as 8; Bazel 9 disabled autoloads and reads the flag as a no-op); run answered `//...` | Expected: a bare `py_binary` or `proto_library` is that module's rule and no BUILD file loads it, so no edge names its consumers. If the Bazel here is not 8 and nothing says so, pin it in `.bazelversion`; `--incompatible_autoload_externally=` (empty) on an unconditional line of `.bazelrc` turns autoload off, after which a toolchain module still answers `//...` under `CAMBI-W014` |
| `CAMBI-W025` | an external repository's own packages couldn't be listed (it didn't load, or one of its packages failed to), or there are more of them than `[externals].index_max_packages` allows, so nothing derived about its shape is used | Fix the fetch, or raise `[externals] index_max_packages` in `cambium.toml`. That key is inside the config hash, so the next run builds cold and mints a lineage (docs/CI.md, "Lineage breaks"). Leaving it keeps the wide answer, which is sound and slower |
| `CAMBI-W026` | a repository rule claims to be a directory of this tree and Bazel's package list for the repository says otherwise; the message names the first difference on each side | Check the rule really roots the repository at its `path` attribute; until they agree, a change under that directory stays global |
| `CAMBI-W027` | a `.bazelrc` `build`/`common` line resolves an external repository's build setting to a target of this tree, so a change to that target moves every target of that repository | Expected on a tree configured this way; the answer is wide by that repository until the flag's readers are known |
| `CAMBI-W028` | a dirty package failed to load under `--keep_going` but its `BUILD` file is still there, so the rows the index already had for it stand. The message names the first five such packages | Fix the load error to refresh them; until then those rows are as old as the last query that loaded the package, and the index is partial and names the package. It is asked for again the next time a change dirties it, and heals then: the index stops naming it once it loads |

## Errors

An error ends the run; exit codes are in the README's table.

| code | when it fires | what to do |
|---|---|---|
| `CAMBI-E001` | internal failure with no specific code: io, protobuf, index or classification | No `help:` line: the message is the error chain, and there is no action it does not already name. A bug report should carry the `--log debug` output |
| `CAMBI-E002` | `cambium.toml` couldn't be read or doesn't parse | Fix the file, or point `--config` elsewhere |
| `CAMBI-E003` | git failed, or a revision is not in this clone | The help depends on the revision. A branch with no local copy whose remote-tracking branch is here: pass that (`origin/main` for `main`, `origin/main~1` for `main~1`). An ancestor of a ref that is here (`HEAD^1`, `origin/main~3`): in a shallow clone, deepen it with `git fetch --deepen=N`; in a full one, the ref has fewer ancestors than that. A remote-tracking branch the clone lacks (`origin/main`, or `origin/main~3`): fetch it by name, `git fetch origin main:refs/remotes/origin/main --depth=N`, since a shallow `git fetch origin main` can leave it only in `FETCH_HEAD`. A bare branch name, with or without an ancestry suffix, with neither a local copy nor its remote-tracking branch here (a depth-1 clone of another branch): the same fetch, then pass `origin/main` (or `origin/main~1`), or check the spelling if it is no branch on the remote. A sha: `git fetch origin <sha> --depth=N`, or deepen with `git fetch --deepen=N`. Anything else: check it with `git rev-parse --verify`. A git failure later in a run carries git's error and says to check both revisions exist and deepen a shallow clone |
| `CAMBI-E004` | Bazel failed, or no workspace was found | Run inside the workspace, or pass `-C`; check `--bazel-binary` |
| `CAMBI-E005` | a `bazel query` failed | No `help:` line: the message carries the query and Bazel's last stderr. Fix what Bazel reports; the query must succeed first |
| `CAMBI-E006` | no index is available for the base, at it or within the ancestor walk, and `--no-full-build` was given | The help: `cambi index build --publish`, or drop `--no-full-build`. With no store configured, the message says so and the help instead says to drop the flag and build the base cold, or to set `[baseline].store` before publishing, since `--publish` with no store is `CAMBI-E008` (checked before anything is built). In a pull-request job, test `//...` instead, or drop the flag to build the base cold on the runner: the store is the post-merge job's to write, and `CAMBI-W003` lines before this mean the configuration changed (docs/CI.md) |
| `CAMBI-E007` | the index on hand used a different `cambium.toml`; splicing could disagree with a full build | Mint a new lineage: `cambi index build --publish` |
| `CAMBI-E008` | no index store is configured: `[baseline].store` is unset, and the verb needs one (`index publish`, `index list`, `index gc`, `--publish`) | The help: set `[baseline].store` in `cambium.toml` |
| `CAMBI-E009` | refusing to publish an index Bazel couldn't fully load: no partial index is allowed here, or one failed that `baseline.publish_partial` does not name, or more packages failed than Bazel named so the list can't be checked | Fix the load errors; name the expected absences in `baseline.publish_partial` (`["//pkg/...", "@repo//pkg"]`); `--allow-partial` overrides for one run |
| `CAMBI-E010` | the store backend failed. `index build --publish` and `index update --publish` ask the store before anything is built, so an unreachable one fails there | Check `[baseline].store` is reachable, credentials current; exit 5, retryable |
| `CAMBI-E011` | an io error against the store: a `dir` store whose path is a file or lies under one, is a symlink to nothing, or cannot be read. A directory that does not exist is not this: it is an empty store (`CAMBI-W007`). With `--publish`, `index build` and `index update` find this before anything is built | Check path/permissions on `[baseline].store`; exit 5, retryable |
| `CAMBI-E012` | the store backend doesn't support the operation: `cambi index gc` on anything but a `dir` store, `cambi index list` on plain HTTP or on a `command` store without `list_cmd`, a publish to a `command` store whose `push_cmd` is empty, a fetch from one whose `fetch_cmd` is empty | The help names the fix for each: garbage collection runs on a `dir` store only, so an S3 or GCS prefix gets a lifecycle rule instead (docs/STORE.md, "Garbage collection"); listing needs a store that can enumerate, a `dir` store or a `command` store with `list_cmd` set; a publish needs `push_cmd` set in [baseline].store, a fetch `fetch_cmd` |
| `CAMBI-E013` | the command line doesn't make sense, e.g. a format a verb can't render, or no range given and no merge base with `[git].default_branch` in this clone | The message names the flag or revision; the `help:` line names the fix, or says `` `cambi <verb> --help` lists what each verb takes ``. A command line the argument parser rejects before `cambi` runs (an unknown flag or verb, a missing value) is not this code: it prints the parser's own message and its `--help` hint, with no code, and exits 1 |
| `CAMBI-E014` | `cambium.local.toml` sets a key that's part of the config hash, deciding the graph, not the machine | Move it into `cambium.toml`; only `bazel.binary`, `bazel.startup_flags`, `baseline.cache_dir`, `baseline.compress_indexes`, `baseline.publish_partial` may appear locally. Of those, the rc-chain startup flags (`--bazelrc=`, `--noworkspace_rc`) are still hashed, so setting them locally makes that machine its own lineage |
| `CAMBI-E015` | the Bazel binary wasn't found on `$PATH`, or printed no version | Install Bazel or bazelisk, or name the binary with `--bazel-binary`, `[bazel].binary` in `cambium.toml`, or `bazel.binary` in `cambium.local.toml`. When `--version` printed nothing, run it by hand: a bazelisk that cannot download a release says why |
| `CAMBI-E016` | `cambi doctor` published a probe object to the store and couldn't read it back. A `dir` store's missing directory is created by the probe, so this means the directory cannot be created or written (a path under a file, a permission), the same failure a run reports as `CAMBI-E011` | Same calls `--publish` uses; confirm `[baseline].store` writable |
| `CAMBI-E017` | a `cambi inspect` query named a label, package or node kind the index lacks | For an unknown package, the help gives the spelling: `//pkg` or `pkg` (the root package is `//`), `@repo//pkg` in an external repository; `cambi inspect owner <file> <path>` says which package owns a path. For an unknown label, `cambi inspect targets <file> <package>` lists a package's targets |
| `CAMBI-E018` | `cambi index update` found the range invalidates everything (reason in the message) and `--no-rebuild-on-global` blocked a fresh lineage | Drop the flag, or pick a splice-able range |
