# `cambi` diagnostics

Every warning and error carries a stable code, assigned once and never reused; retired codes stay, marked retired. Human form follows `rustc`: `warning[CAMBI-W004]: <message>`, `  --> path:line` if located, `  = help:` if fixable. Under `--format json` it's `{"code", "level", "message", "location", "help"}` in the `diagnostics` array; under `jsonl`, one `{"event": "diagnostic", ...}` line each. Warnings never change the exit code; a log line (`--log info`) is never a diagnostic.

## Warnings

| code | when it fires | what to do |
|---|---|---|
| `CAMBI-W001` | a deprecated spelling still worked: `baseline` for `index`, old `index <query>` for `inspect <query>`, `index inspect` for `index show`/`inspect target`/`inspect package`, bare `config` for `config show`, `--output` for `--format`, `text` for `human` | Switch spelling; removed next release. One line per invocation on stderr; `--quiet` silences it |
| `CAMBI-W002` | `cambium.toml` sets a key `cambi` no longer honours | Delete it; message names its replacement, if any |
| `CAMBI-W003` | a stored index was skipped: `config_hash` doesn't match this workspace | Expected after a config edit; `cambi index build --publish` mints a lineage. Repeats mean the store holds another configuration's indexes |
| `CAMBI-W004` | a `.bazelrc` edit could move the graph: a flag on a line the index query reads (`common`, `always`, `query`; under no `--config`, or one in effect) that isn't on the loading-irrelevant allowlist, a `--config` no rc file defines, an unresolvable `import`, a startup flag, an rc file added or removed. The screen only answers when the rc texts at both ends of the range can be read: a `.bazelrc` the run cannot read at either end is in neither chain, so the screen never sees the edit and the invalidator answers it as `CAMBI-W013` instead; run answered `//...` | Allowlist the flag in `[bazelrc].allowlist_extra` if it can't change what `bazel query` loads. A flag under a `--config` the query doesn't run with is already ignored; `[bazelrc].configs` names the ones it does run with. docs/OVER_REPORTING.md has the model and the per-flag evidence |
| `CAMBI-W005` | dirty packages failed to load under `--keep_going` and were tombstoned rather than carried forward: either no `BUILD` file is on disk, so the package reads as deleted, or the `BUILD` file this change edited is the one that fails to load, so rows predating the edit would report its own targets unaffected | Usually broken on this machine; fix if it should load. Consumers count as affected regardless |
| `CAMBI-W006` | `bazel query //...` finished with errors: index is partial | Fix load errors, or name the expected ones in `baseline.publish_partial` (`--allow-partial` for one run) |
| `CAMBI-W007` | a store read came back as absent when it may not be: a `command` fetch failed with stderr output and was read as a miss (the first one in a run; a command that prints nothing when it fails, such as `aws s3 cp --quiet`, gets no warning); a `dir` store's directory does not exist, so it was read as empty (once per run; the run builds cold, or exits 4 under `--no-full-build`); or `status`/`doctor` could not reach the store | Check credentials, the bucket or the path in `[baseline].store`. A missing directory is expected until the first `--publish` creates it; a relative `path` is read from the workspace root. docs/STORE.md, "Misses and outages", says what each backend reads as a miss |
| `CAMBI-W008` | the base index carries no Skyframe loading layer, so which packages the change moved can't be answered; run went global | `cambi index build` against a Bazel that can run `dump --skyframe=deps` |
| `CAMBI-W009` | a changed `.bzl` is one the module system loads (`WORKSPACE` or the module closure) and the index can't name the repositories it defines; run went global | Expected for a workspace-level `.bzl`; else rebuild the index |
| `CAMBI-W010` | retired with the static `.bzl` load closure's witness. The loading layer's `BZL_LOAD` edges are Bazel's own, so there's no stored closure left to be incomplete | Nothing; the code is not reused |
| `CAMBI-W011` | the base index this run computed couldn't be published | Answer unaffected; check store's writable |
| `CAMBI-W012` | dirty set exceeded `limits.max_dirty_packages`; run re-indexed at head | Still exact, just slower. Raise the limit, or 0 to never cold-rebuild |
| `CAMBI-W013` | a changed path matched an invalidator, so everything is affected. A `.bazelrc` edit is one of these whenever the rc screen has no rc texts to diff (no revisions to read the chain from at either end), because the screen defers to the invalidator rather than guessing: the same edit reads as `CAMBI-W004` when both texts are readable | If it can't move the graph, drop it from `[invalidators]`, or add to `[ignore].globs` |
| `CAMBI-W014` | the external-repository stage couldn't account for a change, escalating to global; includes an rc line the query reads changing `--registry` while `MODULE.bazel.lock` didn't move with it | `[externals].enabled = false` disables the stage if precision isn't wanted. For the registry case, commit the regenerated lockfile with the registry change |
| `CAMBI-W015` | a Starlark build setting a `.bazelrc` edit changed couldn't resolve against the index; run went global | Message says why. Move the setting in-repo, or allowlist it |
| `CAMBI-W016` | `MODULE.bazel` and `WORKSPACE` both present with no `.bazelversion`: which Bazel honours depends on whichever runs, describing different graphs | Pin the version or delete the unused file; `cambi status` names the inert one once pinned |
| `CAMBI-W017` | the Bazel that answered `--version` is older than the oldest major cambium is tested against | Upgrade or pin a tested version; untested is unverified, not refused |
| `CAMBI-W018` | a stored index predates this `cambi`'s on-disk format, so it can't be spliced onto | Mint a fresh lineage (`cambi index build --publish`); old blobs age out via `[baseline].retention_days`, or `gc` now |
| `CAMBI-W019` | the store holds a lineage with a mismatched `config_hash`, or from an engine with a different rule-hash or content revision | Expected after a config edit or upgrade; skipped. `cambi index gc` removes it |
| `CAMBI-W020` | `cambi init` found a `.gitignore` not mentioning `cambium.local.toml` | Add the line: it holds machine-local paths and binaries, and committing them makes them everybody's |
| `CAMBI-W021` | `cambi inspect verify` couldn't run `rdeps` for one sampled target, skipped it; `checked` counts only compared targets | Run `bazel query 'rdeps(//..., <label>)'` by hand to see why; other samples' verdict stands |
| `CAMBI-W022` | `bazel mod dump_repo_mapping` stdout wasn't a JSON object, so identity mapping stood in for the real one; a renamed `bazel_dep` can then name the wrong repository | Run `bazel mod dump_repo_mapping ""`, check stdout is one JSON object (a wrapper script printing to stdout is the usual cause); rebuild once fixed |
| `CAMBI-W023` | a `toolchain`, `platform`, `toolchain_type`, `constraint_setting` or `constraint_value` rule was added, changed or removed in some package; or a `register_toolchains` / `register_execution_platforms` call moved in `MODULE.bazel`, in a `*.MODULE.bazel` segment the root includes, or in `WORKSPACE`; or this commit moved an external repository that such a call offers rules from; toolchain resolution has no query-graph edge, so everything is affected | Expected; nothing to configure. The message names the rule, the file or the repository. The rule is by class, not by path, so no `[invalidators].globs` entry is needed for the directories that hold declarations. The rule-class half is decided after the query, so `affected --dry-run` can plan a splice and the run still answer `//...` |
| `CAMBI-W024` | a module Bazel autoloads native rules from (`rules_python`, `rules_java`, `rules_shell`, `protobuf`, `rules_android`) moved in `MODULE.bazel`, its lock or `WORKSPACE`, and the Bazel here autoloads: 8 at its default, or 7.4 with `--incompatible_autoload_externally` set in `.bazelrc` (an unknown version counts as 8; Bazel 9 disabled autoloads and reads the flag as a no-op); run answered `//...` | Expected: a bare `py_binary` or `proto_library` is that module's rule and no BUILD file loads it, so no edge names its consumers. If the Bazel here is not 8 and nothing says so, pin it in `.bazelversion`; `--incompatible_autoload_externally=` (empty) on an unconditional line of `.bazelrc` turns autoload off, after which a toolchain module still answers `//...` under `CAMBI-W014` |
| `CAMBI-W025` | an external repository's own packages couldn't be listed (it didn't load, or one of its packages failed to), or there are more of them than `[externals].index_max_packages` allows, so nothing derived about its shape is used | Fix the fetch, or raise `[externals] index_max_packages` in `cambium.toml` (docs/OPERATIONS.md, Gotchas: it is inside the config hash, so the next run cold-builds); leaving it keeps the wide answer, which is sound and slower |
| `CAMBI-W026` | a repository rule claims to be a directory of this tree and Bazel's package list for the repository says otherwise; the message names the first difference on each side | Check the rule really roots the repository at its `path` attribute; until they agree, a change under that directory stays global |
| `CAMBI-W027` | a `.bazelrc` `build`/`common` line resolves an external repository's build setting to a target of this tree, so a change to that target moves every target of that repository | Expected on a tree configured this way; the answer is wide by that repository until the flag's readers are known |
| `CAMBI-W028` | a dirty package failed to load under `--keep_going` but its `BUILD` file is still there, so the rows the index already had for it stand | Fix the load error to refresh them; until then those rows are as old as the last query that loaded the package |

## Errors

An error ends the run; exit codes are in the README's table.

| code | when it fires | what to do |
|---|---|---|
| `CAMBI-E001` | internal failure with no specific code: io, protobuf, index or classification | Check the message; bug reports should carry `--log debug` output |
| `CAMBI-E002` | `cambium.toml` couldn't be read or doesn't parse | Fix the file, or point `--config` elsewhere |
| `CAMBI-E003` | git failed, or a revision is not in this clone | Names the revision as typed and the fetch that brings it in (a shallow clone: `git fetch origin main:refs/remotes/origin/main --depth=N`); otherwise carries git's error |
| `CAMBI-E004` | Bazel failed, or no workspace was found | Run inside the workspace, or pass `-C`; check `--bazel-binary` |
| `CAMBI-E005` | a `bazel query` failed | Carries Bazel's stderr; the query must succeed first |
| `CAMBI-E006` | no baseline index is available for the base and `--no-full-build` was given | `cambi index build --publish`, or drop `--no-full-build` |
| `CAMBI-E007` | the index on hand used a different `cambium.toml`; splicing could disagree with a full build | Mint a new lineage: `cambi index build --publish` |
| `CAMBI-E008` | no baseline store is configured | Set `[baseline].store` in `cambium.toml` |
| `CAMBI-E009` | refusing to publish an index Bazel couldn't fully load: no partial index is allowed here, or one failed that `baseline.publish_partial` does not name, or more packages failed than Bazel named so the list can't be checked | Fix the load errors; name the expected absences in `baseline.publish_partial` (`["//pkg/...", "@repo//pkg"]`); `--allow-partial` overrides for one run |
| `CAMBI-E010` | the store backend failed | Check `[baseline].store` is reachable, credentials current; exit 5, retryable |
| `CAMBI-E011` | an io error against the store: a `dir` store whose path is a file or lies under one, is a symlink to nothing, or cannot be read. A directory that does not exist is not this: it is an empty store (`CAMBI-W007`) | Check path/permissions on `[baseline].store`; exit 5, retryable |
| `CAMBI-E012` | the store backend doesn't support the operation (listing, gc) | Use a backend that does, or skip it |
| `CAMBI-E013` | the command line doesn't make sense, e.g. a format a verb can't render, or no range given and no merge base with `[git].default_branch` in this clone | Message names the flag; the `help:` line names the fix, or says `cambi <verb> --help` lists what it takes |
| `CAMBI-E014` | `cambium.local.toml` sets a key that's part of the config hash, deciding the graph, not the machine | Move it into `cambium.toml`; only `bazel.binary`, `bazel.startup_flags`, `baseline.cache_dir`, `baseline.compress_indexes`, `baseline.publish_partial` may appear locally. Of those, the rc-chain startup flags (`--bazelrc=`, `--noworkspace_rc`) are still hashed, so setting them locally makes that machine its own lineage |
| `CAMBI-E015` | the Bazel binary wasn't found on `$PATH`, or printed no version | Install Bazel/bazelisk, or name it via `--bazel-binary` / `[bazel].binary` / `bazel.binary` |
| `CAMBI-E016` | `cambi doctor` published a probe object to the store and couldn't read it back. A `dir` store's missing directory is created by the probe, so this means the directory cannot be created or written (a path under a file, a permission), the same failure a run reports as `CAMBI-E011` | Same calls `--publish` uses; confirm `[baseline].store` writable |
| `CAMBI-E017` | a `cambi inspect` query named a label, package or node kind the index lacks | `cambi inspect targets <package>` lists a package's targets; `cambi inspect owner <path>` says which package owns a path |
| `CAMBI-E018` | `cambi index update` found the range invalidates everything (reason in the message) and `--no-rebuild-on-global` blocked a fresh lineage | Drop the flag, or pick a splice-able range |
